# Scene IR 0.17.0

Published. Do not edit. Wire version `"0.2"`.

Minor bump below 1.0 for a new capability contract. Documents still declare `irVersion` `"0.2"` and gate the new feature with `requiredCapabilities` containing `geometry.pathProgress`. A package that does not enable that capability rejects the scene at accept time; older validators reject the unknown `pathAttachments` key and the `path.progress` channel. Decision: `docs/decisions/engine/path-progress-geometry-authoring.md` (E015); landed by E037.

## Capabilities introduced

- geometry.pathProgress

## Representation

Optional scene field `pathAttachments: PathAttachment[]`, also allowed on the `CREATE_SCENE` header (base definitions, frozen after the first seal like `interactions`).

```ts
interface PathAttachment {
  nodeId: string;
  pathId: string;
  progress: number; // [0, 1]
  orient?: boolean;
  rollRadius?: number; // > 0 when set
}
```

- `nodeId` names a root-scene node; `pathId` names a root-scene node of kind `path` other than `nodeId`.
- At most one attachment per `nodeId` (`DUPLICATE_ID`). A non-empty `pathAttachments` requires `geometry.pathProgress`.
- New node track channel `path.progress` (`NodeAnimChannel`, DSL path `path.progress`, number, scalar `path.progress`) with samples in `[0, 1]`. A `path.progress` track is valid only on a node that has an attachment (`INVALID_TRACK_TARGET`).
- Owned channels (`pathAttachmentOwnedChannels`): `transform.position.x` and `transform.position.y` always; `transform.rotation` also when `orient === true` or `rollRadius` is set. Timeline tracks, interaction bindings and physics ownership on those scalars are rejected (`OVERLAPPING_WRITERS`).

## Sampling

`sampleScene` applies attachments after track sampling and trim resolution, so the order stays morph then trim. For each attachment:

1. `progress = pose.pathProgress ?? attachment.progress` (the `path.progress` track wins while active).
2. The path outline is the sampled path commands (`commands` track, else the node's commands), then the same trim rules frame resolution uses (static `geometryOperators` or sampled `trim.*` overrides).
3. `attachAlongPath({ commands, progress, orient, rollRadius })` returns the position, tangent angle and distance (arc length uses the 8-samples-per-curve table shared with `geometry.trimPath`).
4. Position is written to the node's `transform.position`. When `orient` or `rollRadius` is set, `transform.rotation = (orient ? tangentAngle : 0) + (rollRadius ? distance / rollRadius : 0)`. Orientation alone is never rolling.

The position is the path's local command space written directly to `transform.position` (traveller and path share a parent; the path's own transform is not composed). Attachments whose nodes are not present yet are skipped, so streamed partial scenes sample safely. `ResolvedFrame` is unchanged. A scene without `pathAttachments` samples exactly as in 0.16.0.

## Authoring gates assessment

1. **Simplicity.** `pathAttachments` carry a node, a path and one progress number; no arc-length tables or baked keys reach the IR.
2. **Generation.** Additive on existing path nodes and tracks. Existing scenes are unchanged.
3. **Streaming.** Attachments are base definitions on `CREATE_SCENE`; late morph/trim deltas recompute the pose on every sample without rewriting sealed history.
4. **Expressiveness.** Metrics stay in `@gvr/schema` path-metrics and `@gvr/runtime` `attachAlongPath`. Rolling is the explicit `rollRadius` option, not a side effect of `orient`.

## Readers

A 0.17 consumer accepts wire `"0.2"` documents. Migrated 0.1 scenes have no attachments.

## Not in this release

Stroke dash, width profiles, a dedicated marker representation, a standalone `transform.autoOrient` channel, composed path transforms, and adapter lowering from Lottie/SVG.
