# MotionScript 0.17.0

Published. Do not edit. Wire version `"0.2"`.

Minor bump below 1.0 for a new capability contract. Programs still declare `version "0.2"` and gate the new feature with `requires "geometry.pathProgress"` (the compiler adds it when an `attach` declaration or a `path.progress` track is present). A package that does not enable that capability rejects the document at accept time. Decision: `docs/decisions/engine/path-progress-geometry-authoring.md` (E015); landed by E037.

## Capabilities introduced

- geometry.pathProgress

## Syntax

`attach` and `along` are new reserved words. `progress`, `orient` and `rollRadius` are body words that match by spelling (like `interact` body words), so existing identifiers spelled that way keep compiling.

```
path Rail { stroke #38bdf8 width 4; move (60, 90); cubic (200, 10) (320, 170) (460, 90); };
circle Tip { radius 6; fill #fbbf24; };
attach Tip along Rail {
  progress 0.5;       // required base in [0, 1]
  orient true;        // optional: rotation follows the path tangent
  rollRadius 10;      // optional: rolling = distance / radius; NOT implied by orient
};
animate Tip.path.progress { from 0; to 1; duration 2s; };
```

- `attach <nodeId> along <pathId> { … };` names a root-scene node and a root-scene `path` node. A declaration may precede either node; it waits until both exist (forward references defer like `interact`).
- `progress` is required and must lie in `[0, 1]`. `orient` is `true` or `false`. `rollRadius` is a number greater than `0`. A repeated property keeps its last value.
- A node has at most one `attach` (`DUPLICATE_ID`). The target must be a `path` node (`INVALID_GEOMETRY`) and cannot be the node itself.
- `Tip.path.progress` is a new number channel in `[0, 1]`. It is legal only on a node that has an attachment; the track overrides the attachment's base `progress` while it is active. A `path.progress` track waits for its attachment like any forward reference.
- `attach` declarations are base definitions and are frozen after the first `seal`.

## Semantics

Sampling resolves the path's commands in the existing order: path morph (`geometry.pathMorph`) first, then trim (`geometry.operators` / `geometry.animatedTrim`). The node is placed at `progress` of that **resolved** outline (arc length uses the same 8-samples-per-curve table as `geometry.trimPath`). Late morph or trim changes move the node without re-baking `progress`.

The position written is in the path's local command space and is assigned directly to `transform.position`; put the traveller and the path under the same parent and leave the path's own transform neutral. Composed path transforms are outside this release.

Ownership: an attachment exclusively owns `transform.position.x` and `transform.position.y` on its node. When `orient true` or `rollRadius` is present it also owns `transform.rotation`, which is written as `(orient ? tangentAngle : 0) + (rollRadius ? distance / rollRadius : 0)`, with `distance` measured along the resolved outline. `orient` alone is **not** rolling: a wheel that must roll states `rollRadius` explicitly. Timeline tracks, `interact` bindings and `physics` writes on owned channels are rejected (`OVERLAPPING_WRITERS`); a position-only attachment leaves `transform.rotation` free for tracks.

## Authoring gates assessment

1. **Simplicity.** One declaration and one number (`progress`) place a node on a path; there are no arc-length tables, tangent maths or baked position keys. Rolling is one explicit radius.
2. **Generation.** Purely additive on existing `path` nodes and tracks: a model that already emits a rail and a traveller adds one `attach` and, if it moves, one ordinary `animate … path.progress`. Both reserved words are rare; body words stay ordinary identifiers.
3. **Streaming.** Attachments are base definitions on `CREATE_SCENE`, admitted once their nodes exist and frozen at the first seal. The traveller's pose is derived at sample time from whatever geometry is currently resolved, so late morph or trim deltas recompute without rewriting the sealed prefix.
4. **Expressiveness.** Metrics, tangents and distances stay under the hood. Orientation and rolling are separate explicit choices; width profiles, dash (`paint.strokeDash`) and markers stay outside this release.

## Readers

A 0.17 consumer accepts wire `"0.2"` documents. `attach` requires `geometry.pathProgress` in `requires`; the compiler adds it. Older packages reject the capability token, the unknown `pathAttachments` key and the `path.progress` channel. Programs without `attach` compile exactly as in 0.16.0, except that `attach` and `along` are now reserved and cannot be identifiers.

## Not in this release

`paint.strokeDash` (E038), width profiles, markers as a separate declaration, a standalone `transform.autoOrient` channel (still pending), composed path transforms, and Lottie/SVG import of motion paths or auto-orient.
