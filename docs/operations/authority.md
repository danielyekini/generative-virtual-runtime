# Authority and navigation

| Question | Authority |
| --- | --- |
| What are we building and for whom? | docs/project/charter.md |
| What milestones and dependency direction apply? | docs/project/roadmap.md + owning orchestrator's current direction |
| What task/status/priority/owner is current? | Configured GitHub Project + issue/subissue |
| What syntax/semantics exist? | Actual versioned grammar/schema, release pointers/contracts |
| What support is claimed/tested? | packages/schema/capabilities/registry.json, scoped tests/evidence |
| Why was a consequential decision made? | Linked decision record, evidence and status |
| What did one run demonstrate? | Immutable evidence + issue handover |
| What should an authoring model receive? | Generated versioned native authoring reference; not historical plans |
| How do I run autonomously? | Selected repo persona SKILL.md + docs/operations/run.md |

Do not promote planned functionality by editing a summary. Resolve any actual
implementation/contract discrepancy as a work item; never invent support.
Technical contracts constrain implementation; user direction can commission a
versioned change, not silently reinterpret a published program.

Historical fidelity/authoring procedures apply only when the current work item
requires their particular claim. No whole-corpus certification for every native
feature. Existing immutable version/evidence rules are retained. Old process
requirements contradicting this explicitly commissioned operating structure
are superseded for new work after installation; record the supersession map.
Current external protections/permissions are never bypassed by a repo rule.
