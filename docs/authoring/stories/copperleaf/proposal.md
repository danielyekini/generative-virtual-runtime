# Copperleaf Run: language proposal

Retrospective written after the implementation, as supplied, recorded 2026-10-29. Unevaluated; see the [index](../README.md#what-these-proposals-are). Its tables were flattened when pasted and are kept as received.

---

The shipped scene plays the route, and the cuts that hurt it are measurable. The first bitmap scene was rejected at 706 nodes. What remains is a 467-node block scene whose jumps, coins, and cavern ending line up with the storyboard, while the pillar, the grass, and the beetle jump do not.

1. Assess the result
The program is fixtures/motionscript/stories/copperleaf-run.ms, generated by build-copperleaf.ts. It compiles, validates, and samples cleanly: 187,137 bytes, 6,847 lines, 467 nodes, 169 tracks, 0 steps, 5,510 keyframe samples. Pip and the camera stay on a 4px grid for all 2,404 samples taken every 50ms.

What the storyboard gets. Pip enters from the left, reaches the left third of the 1280×720 frame by 2s (screen x 424), and runs through six leg poses with three scarf shapes. Coins disappear at 2s, 3s, and 4s, then on both early arcs, the three stepping-stone beats, and 29s, each with a four-pose spark. The first jump crouches at 5.0–5.3, tucks at 6.2, and lands at 7.2. The beetle is on screen by 10.5 (shell at screen x 1004), passes under the apex at 12.3, and holds a front-facing turn for about 0.2s at 13.1 before following and stopping at the far lip. The stepping-stone lands at 16.7 and 18.8, with the camera raised 64px between them. The flag steps from muted purple to orange before the cheer at 22s, then flutters. The cavern at 30s shows Pip in a run pose, mushrooms, a coin still ahead, and the low step.

Floating tufts, the tree through the apex, and the pillar missing the seam are implementation choices. Groups, z-order, and world space already express the fix.
The blocky cast and the sparse scenery are consequences of the 500-node limit. The first generator, after the step rename, reported Node count 706 exceeds 500, kept 372 nodes, and dropped the whole actors group.

Canvas nearest-neighbor is a suspected renderer gap. This review did not capture a blurred playground frame.

3. Evaluate improvements
Name the budget failure and the reserved word. This solves the compile where the cast disappeared and the errors blamed missing tracks. Before: adding group actors past 500 nodes yields Node count 706 exceeds 500 and then No node id matches actors.pip.position.x. After: one diagnostic names the unit and the limit, and tracks of a rolled-back unit are not reported as unknown. Before: rectangle step yields Unknown property step. After: `step` is reserved; an identifier is required. This improves generation reliability and authoring effort. It does not change playback or the language. Cost is a compiler diagnostic change. Compatibility stays put. Any generated scene near maxNodes, or any identifier that collides with step, hold, complete, and the rest of the keyword list, benefits. Experiment: recompile the saved 706-node source and require a single resource diagnostic that names actors, with no UNKNOWN_TARGET for that rollback.

Repair the choreography with the current language. This solves the pit tuft, the tree through the apex, and the pillar missing the seam. No new syntax. Before: group veil { space screen; …} driven on a 27–28s ramp, and grass rectangles at every 140px including pits. After: the pillar is a world group at the arch, in front of Pip, wide enough that the seam is covered while it crosses the frame. Grass rectangles are emitted only where surface exists. The tree whose canopy is at screen (356, 344) at 12.3s moves off the patrol. This improves visual quality and correctness. Token count barely changes. Cost is a generator edit. Other side-scrollers with foreground layers and wipe transitions benefit only as a technique, which the authoring guide already asks for (hierarchy and explicit space). Experiment: at 6.2s no near-layer rectangle intersects the pit. At 27.5s the arch seam’s screen x lies inside the pillar’s screen span, and Pip’s scarf is outside it by 28s.

Profile the 500-node cap against this scene before adding a sprite construct. This solves the forced drop from the bitmap cast to the block cast. limits.ts already says to profile before treating the number as permanent. The rejected scene was 706 nodes and 247KB, under the 512KB source cap, with the same order of tracks. Raising the cap, if a profile says 700 nodes still render, restores that art with no new semantics. A drawn sprite or a supported image pose is the next step only if the cap should stay: one pose would be one node instead of the 207 Pip rectangles. Hypothetical, and only if the budget stays:


image pipRun0 { href "pip-run-0.png"; size (24, 28); }
That is not a claim that a shorter file generates better. A controlled generation experiment would have to show models emit a valid sprite scene more often than a valid rectangle scene. Cost of a cap change is compatibility with anything that assumed 500. Cost of images is the untested resources.image path plus smoothing, because drawImage uses the canvas default. Other pixel-art and repeated-prop scenes would benefit. One program is not yet evidence for a general symbol system. Experiment: render the 706-node scene with the cap lifted and compare frame time and the 12.3s silhouette to the 467-node scene. Accept a budget change only if the detailed frame stays inside an agreed frame budget. Accept an image pose only if that same frame is crisp at a non-integer contain scale.

Do not add a follow constraint or absolute key times for this file alone. Sparse linear keys would leave subpixel positions when scrubbed between samples. Hold-per-step is what keeps the 4px grid. A shared percent helper already exists in build-counter.ts. Pointing this generator at it is enough. Camera x and y are split because the emitter helper is scalar. A vec2 position channel already exists. Clockwork and counter also key camera components separately. That is a pattern to compare, not proof that a constraint is due.

Do not add audio from this program. The storyboard’s cues are comments. A guide sentence that MotionScript scenes are silent would stop the next generator from inventing a channel. An audio engine is a product decision, not a fix for this picture.

4. Richer output
Pixel-resolution Pip and beetle. The storyboard’s “six distinct running poses” and the copper shell are essential to the requested style. The block poses meet the beat list and lose the silhouette. Achievable only with a higher node budget or a supported crisp image. Denser mountains and grass are the same constraint. Sixteen tufts cannot become a foreground field inside the remaining 33 nodes. geometry.repeater is registered unsupported, so it is not an available way out.

A pillar that actually covers the cut, and a clean apex. Essential to the 0:27 beat and the 0:12 beetle beat. Both are choreography on current groups. Optional polish on top: landing dust on the later taps (the storyboard asks for dust only on the first thud), and a second coin spark frame that reads at playback size. The first spark was a 1-art-pixel spec at z-index 8 and was enlarged after the SVG pass.

Playback of the written sound cues. Essential to the request, absent from the language. Not an art pass.

5. Prioritise
Fix now, in the program. Move the pillar into world space on the arch, stop planting grass over pits, and move the tree off the 12.3s apex. No MotionScript or runtime change. Those three frames are already wrong for reasons the language can express.

Fix now, in the compiler diagnostics. When a unit crosses maxNodes, name that unit and do not follow it with UNKNOWN_TARGET for nodes the rollback removed. When an identifier is a keyword, say it is reserved. Both failures were reproduced on the first copperleaf source.

Experiment next. Profile the rejected 706-node scene. Keep 500 only with a frame-time result in hand. A sprite or image pose is in scope only if that profile says the rectangle grid cannot stay. Defer follow constraints, new keyframe time syntax, drawn symbols as a general feature, and audio. The repeated patterns worth comparing with clockwork and counter are baked per-component camera tracks and percent keys that need extra digits. This one scene does not justify either abstraction.
